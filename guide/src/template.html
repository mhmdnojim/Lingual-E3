    1. Overview

    What the old app was

    The disc contained Oxford iTools 2.0 (2014). It was a desktop program (windows/oup.exe) built on Mozilla XULRunner (an old Firefox engine). It showed book pages with a map library called OpenLayers and played audio, video and answer keys with Adobe Flash Player 13.

    Adobe stopped Flash at the end of 2020, and XULRunner is no longer maintained. The program also checked a licence online. So on a modern Windows 11 computer the app no longer worked.

    What the new app does

    The new version is a small website. A tiny Python server sends the files to Microsoft Edge or Chrome — on your own computer, to phones on the home Wi-Fi, or as a public website (Lingua Books, where anyone can add a text, a PDF or photos of pages and read them the same way). No Flash is needed, and no internet except for the online “Natural” voices and the first translation of a page.

    The content was converted once by build scripts. The page images, audio and answer keys come from the original disc. The page text was read from the page images with OCR, and it is what makes every sentence, clause and word clickable. The recordings that had no script on the disc got one from speech recognition.

    Can another old app be rebuilt as a web app?

    Usually, yes—if you can provide the app folder and the files it depends on. It is a careful rebuild, not a one-click format conversion: first identify the old technology and assets, then reproduce the useful screens and behavior in a browser while keeping the original folder untouched. Results depend on what the folder contains; missing source code, server services, passwords, DRM or proprietary formats can limit what can be reproduced.

    You can add the raw app folder to this workspace or provide it as a ZIP. Include the app files, local data/content folders, and any setup or usage notes. Do not include passwords, private keys, personal user data, or material you are not allowed to copy. Keep the original app and source folder as a read-only reference.

    A rebuild can be tracked with numbered milestones and a real progress indicator. Each step is marked complete only after its checks pass; if a step needs a decision or the source is unclear, it is shown as waiting rather than pretending the work is finished.

    1. Inventory and safety: list files and formats, identify the entry point and dependencies, note licenses and data boundaries, and make a backup/working copy.
    2. Understand the old app: inspect source and configuration, run it safely if possible, capture its screens and workflows, and map its features to the files that implement them.
    3. Plan the web version: agree which features and data to preserve, choose a browser/server architecture, and define what cannot be reproduced exactly.
    4. Build a small pilot: implement the main screen and one representative workflow using a small sample of the original data.
    5. Review and refine: compare behavior and screenshots, collect your corrections, and update the design before scaling up.
    6. Convert in batches: process data/assets with scripts where possible; show per-step and per-batch counts, current item, failures, and a resume option.
    7. Verify and package: test the main workflows in a real browser, check that original data remains unchanged, then prepare run/deploy instructions and backups.

    Technique: use an AI coding assistant to explain unfamiliar code, trace workflows, draft and revise the web implementation, and interpret screenshots. Pair that with ordinary engineering tools—file/type inventories, source search, format-specific parsers, OCR only when needed, checksums, browser automation, and human review. AI is an aid, not a guarantee: generated results must be checked against the original, especially for extracted text and media.

    3. Choose content: select collections, language(s), page range, OCR settings, repeated corrections and whether to preserve supported media.
    4. Review samples: check 1–5 pages, adjust settings and regenerate if needed. Conversion requires explicit approval of the current sample.

Unrecognized formats need another adapter. The export is a content archive, not a standalone website. OCR can make mistakes: review the samples and correct sentences after import.

    Step 3 — Sentences and clauses

    Goal: OCR only gives lines and words. To click a sentence or a clause, the words must be grouped. This is done in four stages in segment_text.py.

    a) Clean the words

    Remove noise: the audio icon is read as @9))) or @10)), and lone symbols have no letters. Fix a common slip: 0K → OK.

    b) Group lines into blocks

    Two lines belong to the same block (paragraph) only if all these are true: similar font size, the gap between them is small, they overlap horizontally, the new line is not further left (a new column), the first line is not a short heading above longer text, and the new line does not start a numbered item.

    Tuning

    The rules were tuned on real pages. Examples: a one-word last line (“context.”) has a smaller box, so the font-size rule only compares lines with 3+ words; the removed audio icon is still used for the line's left edge, so the line is not seen as indented.

    c) Split blocks into sentences

    A word ends a sentence if it ends with . ! ? …, it is not an abbreviation (Mr., e.g., p. …) or an initial, and the next word starts with a capital letter, a digit or a quote.

    d) Split sentences into clauses

    A clause ends after , ; : or a dash. A new clause also starts before a linking word: because, although, when, if, which, who… (both sides at least 2 words), or and, but, or, so (both sides at least 4 words, so “Rutledge and Adam” is not split). One-word pieces like “However,” join the next clause.

      6.1 The local server

      Why it is needed: browsers do not let a page opened from file:// load JSON files, Ruffle needs to load .wasm files with the right type, and audio/video seeking needs “Range requests” (asking for only part of a file). Python's built-in server does not support Range, so server.py adds it.

      • Listens on 127.0.0.1 only — other computers cannot connect.
      • Serves the main folder, so /web/… (the app) and /.shared/… (original audio and answer keys) both work.
      • Tries ports 8765–8784 if one is busy, then opens the browser.

      6.2 The page view

      Each page is a stack of four layers in one box with the page's aspect ratio (1984 : 2496):

      2. SVG text layer with viewBox="0 0 1984 2496". Because the SVG uses the same pixel units as the OCR boxes, the boxes line up at any zoom with no maths.

      6.3 Clickable text: sentence, clause, word

      How it works:

      1. When a page loads, its text JSON becomes a PageText object. It builds two lookup tables: word → sentence and word → clause.
      2. Each word gets an invisible rectangle, widened to meet its neighbours, so there are no dead gaps between words.
      3. When the pointer moves over a rectangle, the app asks unitAt(word, mode) for the sentence/clause/word around it, and draws one rounded rectangle per text line of that unit.
      4. A click sends the unit to the reader (6.5): it reads from there to the end of the page; clicking the same unit again pauses or continues.

      The mode buttons set a class on <body>; with mode “Off” the click targets ignore the pointer, so the page behaves like a plain picture:

      6.4 Text to speech (the “voice”)

      The app uses the browser's Web Speech API (speechSynthesis). Nothing is installed: Edge and Chrome use the Windows voices (David, Zira, Mark — offline), and Edge adds high-quality online Natural voices.

      • Choosing a voice: English voices are ranked: “Natural” first, then US, then UK.
      • Ignoring old events: every speak() increases a counter, so events from a cancelled sentence are ignored.
      • Offline fallback: if an online voice fails (no internet), the same text is spoken again with an offline voice.
      • Word highlighting: the browser fires a boundary event with a character position for each word. The app remembers where each word starts in the spoken text, so it can find the word and highlight it.
      • Clean speech text: bullets are removed, p.104 becomes “page 104”, dashes become pauses, and exercise numbers glued to words (2was) are removed.

      6.5 Read aloud: click, pause, continue

      You doWhat happens
      Click a sentence (or clause)If one of your My audio MP3s contains it, that MP3 plays from there. Otherwise reading starts there with the live voice and goes on to the end of the page (both pages in two-page view).

      Voice settings → Pause between sentencesAfter each sentence (or clause) the app waits the chosen time — none up to 10 s — before reading the next one: time to repeat it aloud. The bar counts down (“Next sentence in 3 s”).

      How it works: the Reader has a state (idle, playing, paused) and a queue of units from the clicked one to the end of the visible pages. When one unit ends, the next starts.

      • Pause stops the speech engine but remembers the last word reported by the boundary event. Continue speaks the same unit again from that word. This works with every voice, even ones where the browser's own speechSynthesis.pause() is unreliable.
      • Smooth flow: every request to a voice takes a moment to start (the online Natural voices wait for Microsoft's server), so reading sentence by sentence left a gap after each one. speakFrom therefore gives the voice up to 10 sentences (1,500 characters) of the page in one request. The voice reports the position of each word; from it the app knows which sentence is being read and moves the highlight. One sentence at a time is used only when a pause between sentences is chosen, in word mode, and for voices that report no word positions.
      • Pause between sentences: when a unit ends, finished() waits settings.gap seconds before the next one (tickWait() updates the countdown). The finished sentence stays highlighted. Pausing during the wait and continuing goes straight on to the next sentence.
      • Each new sentence is centred in the Text list (centerPanel) and kept visible on the page (reveal). A click on the page also switches the side panel to the Text tab.

      Repeat each sentence

      The Voice tab has Repeat each sentence: once (normal), 2 to 10 times, or ∞ (the slider's last step) — the same sentence again and again until you click another one, pause or stop. The reader keeps a counter (round): when a sentence ends, finished() reads it again until the count is reached, then goes on; the pause between sentences is also made between the repeats, and the bar shows “2nd time of 3” or “6th time, ∞”. Repeats are read one sentence per request (not in the 10-sentence pieces). With a My audio MP3 the same setting works by jumping back: when the MP3 reaches the next sentence by itself, it goes back to the start of the one being repeated (follow; the last sentence on the ended event); in Word mode the word is played again after a short silence.

      Quicker than the slider: the repeat button in the top bar, next to the translate button (or R). Each click goes 2 → 3 → 4 → 5 → ∞ → once; a small badge on the button shows the number (none for once). It changes the same setting as the slider, so both always agree (cycleRepeat, showRepeat).

      Read an area of the page

        How it works

        1. Editable model. The flat page format (words + ranges) is turned into nested lists: paragraphs → sentences → words. Every correction is a small function that changes these lists. Then the model is turned back into the flat format, and clauses are recalculated with the same rules as the build (segment.js). Converting all 472 pages to the model and back gives exactly the build's files — this was checked.
        2. Keeping the boxes. When a sentence's text changes, the new words are matched to the old words (longest common subsequence). Unchanged words keep their box. A changed word takes the box of the word it replaces; a split word (“Doyou” → “Do you”) shares the old box by character length; joined words get the union of the boxes. New words have no box.
        3. Staying on the same sentence. The app remembers the sentence you are on (being read, last read, clicked or corrected — currentFocus). Correction mode opens with it selected and centred; Done goes back to reading with the same sentence highlighted and centred (setFocus).
        4. Drag and drop. Built with pointer events rather than the browser's HTML drag and drop (which in testing sometimes ended without a drop), so it works the same with a mouse, pen or finger. Only the handle starts a drag (so text can still be selected), after the pointer moves 5 px; Esc cancels. While dragging, dropTarget finds the gap under the pointer; in the gap between two paragraphs, the upper half means “end of the paragraph above” and the lower half “start of the paragraph below”. The drop runs the moveTo correction, so Undo works as usual.
        5. Saving. After each change the whole page is sent to the server (PUT /api/text/…) 0.4 s later. Saves of the same page run one at a time, so the newest version always wins. The server checks the data and writes web\edits\<book>\<page>.json. Pages without corrections still come from web\data\text.

        Reading an area again with OCR

        The box is drawn in page pixels (the same units as the words). The server crops that part of the page image, reads it with the book's OCR (library.read_png: Tesseract or Windows OCR), moves the words back to page coordinates and makes them page text with the same rules as when the book was made (library._doc, which also leaves out pinyin for Chinese books). Nothing is saved yet: the editor shows the sentences found and how many words are in the box now, and the person adds them or lets them replace those words. The paragraphs found stay paragraphs: each row of a list of new words, for example.

        Lists of new words

        A box of new words (生词 New Words) has rows of a number, a Chinese word, its pinyin, its part of speech and its meaning, in columns: “⑧ 服务 fúwù v. serve”. OCR reads such a box line by line across the page, so its rows would come between the lines of the dialogue beside it, and a meaning on several lines (centred on its row: the first lines are above the word) would be cut from its word. segment_text.word_lists finds the list by its parts of speech one under the other (n., v., adj., m., suf. …, at least 3), the words' column (where words in Chinese start in half the rows), and where the meanings start. Rows whose part of speech OCR misread are found by their word or pinyin in its column. The meaning's lines are shared out among the rows so that each row's meaning is around its middle (or starts at its top), and a line on a row's line goes with that row. Each row becomes a paragraph of its own, in the list's order, after the list's title: the word (a sentence as it is), then the meaning; the number, pinyin and part of speech are left out with the pinyin. A list next to another one, or text beside it, ends where a wide gap or another row starts. The table of the parts of speech itself (name, English, abbreviation: nothing after the abbreviation) is not a list.

        Choices of an exercise

        The choices of an exercise are often on one line: “A 换房子 B 买空调 C 去女儿的初中”. segment_text.choice_starts finds their letters one after the other in a line (A, B, C …, also “a)”, “(C)”, and “_C” as OCR reads it), each with words after it, the first at the start of the line (or three from A), and makes each choice a sentence; so is each question (“(2) …” at the start of a line, or after the last choice on its line). Two letters joined by a word are no choices (“neither A nor B”), nor a number in English going on (“sentences ⏎ (10) to compare”). SENTENCE_RULES 4: the library's pages made before are cut so once, when the app starts (the owner's corrections only cut, by split_languages).

        The speakers of a dialogue

        Under the picture of each speaker of a dialogue there is their name, in small characters (“刘明”). Read with the dialogue, the name would be read as part of what is said. library._speakers finds the lines of 1 to 4 characters much smaller than the page's (measured by their longer side, so a flat “一” is not small) and the pictures as OCR reads them (“(O”, “(0)”: round, bigger than the text), and _doc leaves them out in Chinese books. SENTENCE_RULES 5: pages made before lose them once (drop_speakers).

        Full stops OCR did not read

        Windows OCR often leaves out the “。” of Chinese in a larger print, and a paragraph without its stops is one sentence. Every character takes a cell of the same width, and so does a stop: segment_text.missed_stops looks at the page picture where a cell is empty after a character (between two, or at the end of the line) and finds a small ring low in it, with nothing above it (_ring: not a comma, a dot, or a closed part of a character as 口). The stop is put on the character before it, so the sentence ends there; a “0” or “o” OCR read for one becomes “。” too. Only for words read by OCR (_doc(…, stops=True): areas, the whole page, scans and photos): the boxes of a PDF's text do not fit the picture closely enough, and it has its stops. SENTENCE_RULES 6: the owner's corrected pages get their stops back once, and are cut only there (restore_stops, cut_after).

        6.18 My audio: MP3s with a natural voice

        Any paragraphs or sentences of a page can be turned into one MP3 read by a Microsoft Natural voice or by a Windows voice installed on the computer that runs the server (David, Zira, Huihui… — made without internet). An icon next to the paragraph plays it, the text is highlighted sentence by sentence and word by word while it plays, and the My audio tab keeps all of them (play, download, rename, delete, filter, search). Options in the dialog: Read the translation (each sentence's translation after or before it, with a voice of that language), a second voice for speaker B in dialogues (A: … B: …), and for Chinese books a Chinese voice (English only, Chinese only, or both).

        How it works

        1. Why the server makes the MP3. The browser's speech engine can only speak; it cannot save what it says. So the local server (web/tts.py) uses edge-tts, a Python package that talks to the same online Natural voices Microsoft Edge uses for Read Aloud. Creating needs the internet; the MP3 then plays offline. (edge-tts uses Edge's service without an official licence for other apps, so Microsoft could change it — the official alternative is Azure Speech with a key.)
        2. Pieces of up to 10 sentences. The chosen sentences are spoken in pieces of up to 10 (four requests at a time), so they flow like normal reading. The voice reports the time of every word (WordBoundary).
        3. Cutting and joining. ffmpeg decodes each piece to raw sound. From the word times, each sentence's part is cut out with 0.25 s of silence on each side — the voice itself pauses about 0.85 s at every full stop, so this gives an even 0.5 s between sentences (measured: every cut falls in silence). The chosen pause is added between sentences, and ffmpeg encodes one 64 kbit/s MP3 (with the title as MP3 tag). A file <id>.json next to it keeps the title, voice and the start/end of every sentence and word.
        4. Matching words. The words the voice reports (“page”, “104”) are matched to the page words (“p.104”); words it does not report get times shared out by length (_word_times).
        5. Clicking a sentence plays the MP3 first. Before reading a clicked sentence with the live voice, the app looks for an MP3 of this page that contains it (locate: the one in the player first, then the newest). If there is one, the MP3 plays from that sentence — no internet needed; clicking the same sentence pauses, another one jumps. Clause mode starts at the clause's first word, word mode plays just that word. Only sentences without an MP3 use the live voice, and without internet the live voice switches to an offline Windows voice at once.
        6. Subtitles. Every MP3 gets <id>.srt and <id>.vtt with the time of each sentence (made from the JSON timing, also for MP3s made earlier); CC in the list downloads the .srt.
        7. Playing. The normal audio player plays the MP3. Every frame it reports the time; the app finds the sentence and word at that time and highlights them on the page and in the text (follow). If the text was corrected after the MP3 was made, each sentence is found again by its text.
        8. Windows voices. web/windows_speech.ps1 uses .NET's System.Speech: list gives the installed voices (ids start with windows:), speak returns a WAV and the time of every word. tts.py then cuts and joins the sentences exactly like the Natural ones. The voices of the server's computer are listed, never those of another machine, and the app never silently swaps one voice for another.
        9. When Microsoft refuses. Since October 2026 Microsoft answers HTTP 403 to the Natural voices at edge-tts's old address in many countries; tts.py uses the address Edge itself now uses (api.msedgeservices.com), and if a voice is still refused the app says so and suggests a Windows voice.

        How it works

        1. Which translator. The local server (web/translate.py) uses Google's free translators — no account or key. First the address Chrome uses for “Translate this page” (translate-pa.googleapis.com/v1/translateHtml); if it fails, the older address (translate.googleapis.com/translate_a/single?client=gtx). Microsoft's free address, the first idea, no longer answers (404). These are not official APIs for other apps, so they could change one day; the official alternative is the Google Cloud or Azure Translator API with a key.
        2. Whole paragraphs, but every sentence comes back on its own. A sentence translated alone loses its context (“he”, “it”, tenses). So each paragraph is sent as one piece with its sentences marked: <a i=0>First sentence.</a> <a i=1>Second one.</a>. Google translates the paragraph as a whole and keeps the marks, so each sentence's translation is found by its number. A normal page is one request (about 1 s). If Google ever moves a sentence into another one, those sentences are sent again one by one. A paragraph with sentences in two writings (a Chinese sentence, then the book's own English for it) is sent one sentence at a time from the start: together, Google moves words of the Chinese sentence's translation into the English one's mark (“…resolve issues” | “related to lost items.”).
        3. The backup address. It answers in pieces [translation, original]. The originals, put together, are exactly the text sent, so each piece's position shows which sentence it belongs to (_align).
        4. Not too fast. Google blocks a computer for a while when it gets many requests in a row (it then sends every request to its “unusual traffic” page). So requests to the same address are at least 0.4 s apart, Translate the whole book waits 1.5 s after each page that really needed the translator, and an address that answers “too many requests” is left alone for 2 minutes (4, 8… up to 30 if it happens again) instead of being asked again at once. The server tells the page how long to wait (HTTP 429 with wait); the book translation shows a countdown and goes on by itself, and the Text list tries again by itself.
        5. Saved once, offline after. The result is saved in web\translations\<language>\<book>\<page>.json, keyed by the English sentence. Opening the page again reads the file (no internet). A sentence that was corrected is new text, so only its paragraph is sent again. Single words (Word mode) are saved in <language>\words.json.
        6. Words in context. A word means different things in different sentences, so a word is translated in its sentence: the sentence is sent with the word marked, and the marked part of the answer is its meaning there. These are saved in <language>\words-context.json, keyed by the word, its sentence and where it is in it. With cachedOnly (the offline setting) the server answers only from saved files and reports what is missing.
        7. In the page. translation.js asks for the page's translations once per page version and language, then puts a <span class="tr"> after the last word of each sentence in the Text list, with dir="rtl" for Arabic, Persian, Urdu, Kurdish and Hebrew. The box on the page shows the sentence translation at once and adds the word when it arrives. It is placed under the whole sentence (all its lines), above it if there is no room, else beside it, and it moves with the page when you scroll — so it never covers the sentence you are reading.

        6.22 Lingua Books: the library, accounts, a public website

        The same reader opens any book: a text, a PDF, a Word file or photos of pages. The home screen is a library with tabs: Public library (books shared with everyone), My books (private until shared), On this computer (only on this computer: the disc's three books) and, for admins of a website, Admin.

        Kind of bookHow its pages are made (library.py, in the background)
        TextSet into pages of 1200 × 1700 px with the Atkinson Hyperlegible font (made for readability). Every word is drawn by the app, so its place is known exactly; paragraphs, headings (#) and line breaks are kept; a picture can go under the title.
        PDFEach page is drawn with pypdfium2 (1600 px wide); its words and their places come from the PDF itself with pdfplumber, grouped into lines. A page without text (a scan) is read with OCR.
        PhotosTurned upright (EXIF), made at most 2000 px wide, read with OCR (ocr.py: Tesseract on the Linux server, the OCR built into Windows on this computer).

        Then the same steps as for the disc (segment_text.py: lines → paragraphs → sentences → clauses) give each page its words, sentences, clauses and paragraphs, so everything else — reading aloud, translation, repeat, MP3s, corrections — works the same. Each page keeps its own size (the disc's pages are all 1984 × 2496).

        Designs of the pages

        A textbook repeats a few designs of page (in every unit the same page of dialogues with their new words beside them, of grammar, of exercises). Before the first sample of a PDF or photos, designs.py finds them, and the owner tells the app what to read on each — once for all its pages:

        1. Finding them. Every page is drawn 360 px wide (some seconds for 200 pages) and reduced to a grid of 16 × 22 cells: how much ink and how much colour is in each. Two pages are as far apart as their cells differ (the least of three shifts of one cell sideways: left and right pages). The most alike pages and groups are put together, by the average distance of their pages, until the groups of a few pages (two, or 3 % of the book) have 85 % of the pages, 8 groups at most — and as long as they are much more alike than two pages of the book as a rule (half the median distance); but never pages hardly more alike than that (0.85 of the median: in the designs of the textbooks tried, their pages are 0.44–0.79 of it apart; all the pages of a magazine-like book, 0.96). So many, not how alike: books look alike in very different measure (a typical distance of 24 in one book, 81 in another). The pages of the small groups go with the most alike design if near; the rest have no design. On the books tried: HSK Standard Course 2 (152 pages) gives the two pages of dialogues of every unit (15 each), the 83 of grammar and exercises, two small ones; American English File 3rd edition (168 pages, each laid out differently) one of 93 pages, two small ones, 62 pages with none.
        2. Their areas. The first sample is a page of each design (its example, the most like the others). What the app reads on it becomes the design's areas: each list of new words one, paragraphs one under the other close together one (lines left out between them, as the pinyin over a dialogue's lines, join them too), in the order they are read. An area is text, a dialogue (two lines start with a speaker's name: read without them), new words (under a heading “生词”, “New Words”: each row its word, then its meaning — also when its columns are not found, _list_rows) or not read.
        3. The owner checks and changes them (js/designs.js): draws, moves, sizes, removes areas, says what is in each and their order, moves pages to another design, to none or to a new one; saved with PUT /api/books/<id>/designs (checked: designs.clean), then the sample is read again so. Only then are they used (designs.plan: "checked"): until the owner has looked at them, every page is read whole, as before. Laid on other pages that only look alike, an example's areas can cut their text wrongly — on a page of American English File an article came out as “In as it / the / In / you / ate risk / up.”, 88 sentences instead of 65.
        4. Reading a page by them (_doc_in_areas): each word goes in the area its middle is in (the smallest, in one drawn in another), else in the nearest one — a dialogue a little longer than its example's is not lost; the words of an area not read go. Each area is read as a page of its own (_doc, with its kind), and their documents joined in the areas' order. The picture and the frames are one SVG, so they grow and shrink together.

        Replacing a picture on a page

        In correction mode, Replace a picture: the owner draws a box around a picture and gives a new one — a picture of their own, or one OpenAI's image service makes: without a description, the old picture made again (/v1/images/edits with it, pictures.AUTO, and the 60 words of the page nearest the box, to go with); with one, as described (/v1/images/generations, or from the old picture). Each try is shown first and kept in a row, to make another until one is liked, then used — only for admins, as each costs money; its key is kept in server-config.json (auth.set_config, which keeps the PIN). pictures.py fits it to the box (filling it, cut at the edges, or whole on white). Nothing is changed in place: each replacement is kept (pictures.json, pictures/<id>.jpg) with the page picture and the PDF as they were (pictures/page-<n>.webp, source/book.original.pdf), and the page and the PDF are made again from them with all the replacements — so any one can be taken back. In the PDF (pypdfium2): the box from the page picture's pixels into the page's points (from its crop box; from the bottom), the picture objects inside it and the text whose middle is in it taken out, the new picture put in as a JPEG. A scanned page is one picture: the new one goes over its part. The words of the old picture leave the page's text (as made, and as corrected). The book's version (updated, in the pictures' addresses) goes up with each change, even twice in a second: browsers keep page pictures a year.

        A book's audio and video

        The book's Settings → Audio and video: the owner chooses a folder (<input webkitdirectory>) or files; the page sends each audio or video file (PUT /api/books/<id>/tracks?name=), kept by its content as an old app's recordings (migration-media/<sha256>.mp3: served to the book's readers, in parts; transcribed by speech recognition when it has no script). tracks.py takes each one's number from its name (…_1.26.mp3: 1.26; 1.02 and 1.2 are one) and finds it on the pages: with its ⊙ (OCR: “01.26”, or a “0” before it) or with two digits after the dot anywhere; with one digit (a decimal, perhaps) only as the first or second word of a line. A play button goes over the ⊙, on every page where the number is (also in the audioscripts), in migration-assets.json with the page's other buttons (ours marked added: made again when placed again, taken out with them). On American English File 3rd edition Level 3: 239 of the 248 recordings on their pages, 276 buttons on 111 pages.

        Changed by hand (correction mode → Play buttons, playbuttons.js): the page's audio and video buttons get a dashed outline and a ×, and do not play. One dragged elsewhere (off the number it covers) is moved (PUT /api/books/<id>/buttons/<n> {src, from, x, y}); its × takes it away (DELETE …?src=&x=&y=); Add a play button… lists the book's recordings (those on no page first, found by typing), or adds another file, and the next click on the page puts its button there (POST … {file, x, y}). A button of ours moved becomes manual (kept when placed again); on the page where one was moved or taken away its recording is not placed again (skip in its item of tracks.json). Take them all out takes the manual ones too.

        Accounts and who may do what

        • On this computer (server.py): no login; everything belongs to you, the admin.
        • Home Wi-Fi (--lan): the PIN, then as on this computer.
        • Public website (--public --proxy): anyone reads the public books; adding books, MP3s and corrections need an account.         6.23 Following the reading

        While the app reads (or an MP3 plays), the sentence being read stays in the middle of the page and of the Text list — but the person decides: when they scroll, swipe or zoom the page themselves, it stays where they put it, and it follows again by itself after the chosen wait. Meanwhile, if the word being read is not on the screen, it is shown at the top middle of the page, word by word, with an arrow to where it is (up, down or sideways); a click on it brings the reading back to the middle. A plain tap on a sentence does not count. Settings → Follow: on/off (also the target button in the reading bar, and F), where on the page (middle, near the top, only when it leaves the screen), the scrolling speed (or jump at once), the wait after scrolling, and whether the Text list follows too.

        1. Who is scrolling? follow.js watches each area (the page, the Text list) separately: a mouse wheel, a finger that moved more than 10 px, two fingers (zooming) — or a scroll right after the person pressed something there (scroll bar, keys) — is the person. Scrolls caused by the layout (the panel getting taller) and by the app's own scrolling do not count.
        2. Its own smooth scrolling (eased, with the chosen duration) instead of the browser's, so the speed can be set and the app knows which scroll events are its own; the person's wheel or finger stops it at once.
        3. Where the middle is: the part of the page that can be seen — above the reading bar, and on phones above the panel at the bottom. A sentence taller than that is shown from its start.

        1. One file per person. words.py keeps {categories, items} in web\words\words.json (on a website one per account), so the computer and the phones on the home Wi-Fi share it.         6.25 Speech recognition: scripts for recordings without one

        204 of the disc's 319 recordings and videos came without a script. Their scripts are made on this computer by faster-whisper (OpenAI's Whisper model, run with CTranslate2 on the processor; the English model base.en), one line per sentence, so they can be clicked, repeated and translated like the disc's own. The Script tab says “Made by speech recognition: it may have mistakes.”

        1. Once: double-click Setup transcription.bat. It installs faster-whisper into web\vendor\python (apart from the app's own packages) and the model into web\vendor\models\base.en (about 420 MB). No internet is needed afterwards.
        2. All at once: python web\tools\transcribe_all.py (a few seconds per recording; those done are skipped). The results are kept in web\transcripts\<id>.json; build_data.py copies them to web\data\scripts and marks them "auto": true in books.json. Others need only web\data, not the setup.
        3. One at a time: a recording without any script shows a Transcribe button (POST /api/transcribe); it runs in the background, one at a time, and goes on if the player is closed. The disc's recordings without a script and the recordings added to a library book can be transcribed.

        Or ElevenLabs (on the internet)

        With a key of ElevenLabs (Speech to Text, model scribe_v2) saved by an admin — the Script tab's Transcribe a file… or the sliders button next to Transcribe open the Speech recognition window — every transcription is made by ElevenLabs instead: better, with the speakers told apart, in 90+ languages, quick, and on a website too (there only admins start one: each hour of sound costs credits). The key is kept in web/server-config.json (speechKey; speechEngine: "local" when This computer is chosen again), never sent to a page (GET /api/speech-ai says only whether there is one). eleven() sends the file (of a video only its sound, when ffmpeg is here) with diarize and word times; eleven_cues() puts each word's spacing before it, as Whisper's words have, names the speakers A, B and Explanation in the order they first speak (none when one voice speaks), and the same sentences() makes the lines. Its refusals are told plainly (a key that is not accepted, no credits left, busy).

        • All the recordings of a book: its Settings → Audio and video → Transcribe them all (POST /api/books/<id>/tracks/transcribe): those not done yet, three at a time; the box says how many are done.
        • Any file: Transcribe a file… sends it (POST /api/transcribe-file?name=, up to 1000 MB; its language found by itself); its lines come back (GET …?job=, with the language found and a script id, AU- + the sha256 of the file) and are shown under the file as a book's script (Transcript, ScriptTranslation: a click plays a line, again pauses; repeat; the two translation buttons and Translate into, translated from the language found and kept under the "book" files): copy them, or download them as text or as subtitles (SRT). The file is not kept, its lines for an hour.
        • The books on this computer (Levels 1–3): the ⋮ menu → Scripts of its audio and video… (GET/POST /api/disc-scripts/<book>): its recordings and videos without a script on the disc written all again, by ElevenLabs (those it did are skipped; on this computer those it wrote before are done). The player then asks for the saved lines of a recording marked auto too, and shows them instead of the ones built into web/data/scripts. Level 1: 325 (5.2 hours), Level 2: 249 (3.9 hours), Level 3: 204 (3.0 hours).
        • A recording added to a library book is translated like the disc's: its script id is AU- + its file's sha256.

        From Whisper's pieces to sentences

        Whisper returns pieces with the time of every word. sentences() starts a new line at a full stop, question or exclamation mark — but not after Mr., Dr. …, and after U.S. or a.m. only when a capital follows — and also at a pause over 1.2 s, in long stretches without full stops, and for lists of single words (pronunciation exercises). Each line starts at the time of its first word. Phrases Whisper is known to “hear” in silence or music (“Thanks for watching”) are dropped, and vad_filter with hallucination_silence_threshold keeps it from inventing words in silence.

        10. Troubleshooting

        The app says “The book data could not be loaded”

        The page was opened directly as a file. Start it with Start Lingua Books.bat instead (see 6.1).

        The black window says “Python is not installed”

        Install Python 3 from python.org and tick “Add python.exe to PATH”, then start again.

        Nothing is spoken / “This browser cannot read text aloud”

        Use Microsoft Edge or Google Chrome. Check that Windows has voices: Settings → Time & language → Speech. Try the “Test voice” button in the voice settings.

        A “Natural” voice stops working

        These voices need internet. The app switches to an offline Windows voice by itself and shows a message. You can also choose David or Zira in the voice settings.

        An answer key shows “could not be shown”

        Ruffle is missing. Run build_all.ps1 again — it downloads Ruffle into web\vendor\ruffle when it is not there.

        A video does not play

        Check that web\data\video has the MP4 files. Run python web\tools\convert_videos.py again; it only converts missing ones.

        OCR says “English OCR language is not installed”

        Add “English (United States)” in Windows language settings, then run the build again.

        Some text is wrong or a sentence is split badly

        OCR is very good on normal text but can be wrong on small labels on pictures. Splitting rules are in segment_text.py; after a change, run only python web\tools\segment_text.py. You can also correct a word by hand in the page's JSON file in web\data\text.

        Correction mode says “Not saved”

        The app could not reach its server. Check that the black window is still open (or start the app again with the .bat file), then make any small change again — the whole page is saved each time.

        Translation says “The translation failed” or “busy”, or does not appear

        “Busy” means Google got too many requests from this computer in a short time: the app waits the time shown and goes on by itself. Otherwise: the first translation of a page needs the internet. Check the connection and open the page again (or switch translations off and on with L). Pages translated before work offline. If it says the server is an older version, close the black window and start the app again.

        The port is already in use

        The server tries the next 19 ports by itself. The black window shows the address it used.

        Creating an MP3 says Microsoft refused the voice (HTTP 403)

        Microsoft refuses its Natural voices at times, in some countries. Try again later, or choose a Windows offline voice in the dialog (made on this computer, no internet). The app never changes the voice by itself.

        The Transcribe button says the speech model is missing

        Run Setup transcription.bat once (it needs the internet to download about 420 MB), then restart the app.

        A page says OFFLINE but a sentence is read with the live voice

        The badge is about the page's voice files for the chosen voice. Sentences added or changed after the voice file was made, or another voice chosen in the settings, use the live voice. Generate again for the page: only what is missing is made.

        The tests say “Failed to launch the browser process”

        Edge sometimes does not start without a window (for example while it updates). Run the tests with Chrome: $env:BROWSER = "C:\Program Files\Google\Chrome\Application\chrome.exe", then node ui-test.mjs.

        11. Known limits

        • OCR text can contain small mistakes, mostly in labels on pictures and maps, and some exercise numbers stick to words.
        • 156 Teacher's Book pages are not on the original disc, so they cannot be shown.
        • Natural voices need Edge and an internet connection; offline voices are more robotic.
        • Ruffle plays the answer keys well; other old Flash parts of the disc (interactive exercises not linked from the pages) were not used.
        • Translations are machine translations (Google Translate): good for understanding, not always perfect. The free addresses are not official APIs and could change, and Google limits how fast they may be used.
        • Speech recognition scripts can contain mistakes (names, numbers, overlapping speakers); the app says so on each of them.
        • Offline voice files are kept in the browser's storage, which the browser may clear; export them to keep a copy.
        • Python must be installed to run the small server.
        • The website serves many readers on one core (6.21), but makes books one at a time, and the free translator limits how fast it may be used.
        • The rebuilt app is for use on your own computer. The book content belongs to Oxford University Press.

        12. Rebuild it in React (Lovable or another AI)

        The app is plain JavaScript on purpose (3): nothing to install or compile. To rebuild its browser part as a React app — for example with Lovable, which builds React apps from prompts — give the builder the React kit. Lovable cannot import an existing code base, so it builds the app from a specification, step by step.

        The plan in short

        • Keep the server. OCR, PDFs, translation, natural-voice MP3s, speech recognition, accounts and the library cannot (or must not) run in a browser. The React app calls the same API (6.1); in Lovable's preview it uses the sample book instead (VITE_API_MODE=mock).
        • Same origin. The server refuses changes from other sites (same_origin() compares Origin and Host), so the built app is served by the server itself; in development a Vite proxy with changeOrigin: false.
        • Engines outside React. The reading queue, speech, the audio player, following and the correction model stay plain TypeScript; components subscribe to them, so highlights that change many times a second do not re-render the page.
        • Ported exactly: PageText, speakable, clauseRanges/tokenize, the correction model and fold — the same results as now, page for page.
        • Same addresses and settings: #/<book>/<page> routes and the aef3. settings keys, so bookmarks and settings carry over.
